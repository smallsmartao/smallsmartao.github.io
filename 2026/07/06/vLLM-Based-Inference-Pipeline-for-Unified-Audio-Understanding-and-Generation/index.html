An Efficient vLLM-Based Inference Pipeline for Unified Audio Understanding and Generation

本文最后更新于 2026年7月6日 下午

为什么需要这篇工作？

当前大型语言模型（LLM）的推理引擎——以 vLLM、SGLang 为代表——在文本生成场景中已经做到了极致的吞吐优化：连续批处理（Continuous Batching）、PagedAttention、自动前缀缓存等技术将 GPU 利用率拉到了很高的水平。然而，当我们试图将这些引擎用于语音语言模型（Speech Language Models, SpeechLMs）时，会遭遇结构性的架构冲突。

问题的根源在于：语音不是文本。文本生成是”一次一个 token”的单流自回归过程，而高保真语音生成需要多码本（Multi-Codebook） token 的同步预测——每个时间帧被编码为多层残差向量量化（RVQ）token，再经过延迟模式（Delay Pattern）交错排列。此外，高质量音频合成还严重依赖分类器无关引导（Classifier-Free Guidance, CFG），而 CFG 需要每一步同时执行条件和无条件两次前向传播，直觉上会将吞吐量减半。

本文（CMU + 上海交通大学，2026年7月）提出了一套基于 vLLM 的统一推理管线，在不侵入式修改调度器和 PagedAttention 基础设施的前提下，原生支持多流采样、延迟模式去交错和 CFG 的高效执行，实现了相较于顺序 PyTorch 推理 ~100× 的吞吐提升，且 CFG 模式下仍保持非 CFG 吞吐量的 80%。

1. 背景：Speech Language Model 架构

本文面向的模型家族共享以下架构基础（如 Figure 1 所示）：

1.1 多 Token 预测（Multi-Token Prediction）

音频编码器将连续语音送入自回归 LLM。LLM 在统一词表上运行，词表被划分为文本子词表和 $S$ 个音频子词表。在音频输出阶段，每一步 $t$，LLM 骨干产生隐状态 $h_t$，然后 $S$ 个并行的码本头（Codebook Head）将该状态投影为各自的 logits $\ell^{(i)}$ 和采样 token $c_i$（$1 \le i \le S$）。具体地，每个头将一个可学习的流嵌入 $e_i$ 加到 $h_t$ 上再通过共享的语言建模头 $W_H$：

1.2 延迟交错模式（Delay Interleave Pattern）

在延迟模式下，第 $i$ 个流偏移 $i$ 步——即步骤 $t$ 发射的 $S$ 个 token ${c_1, \ldots, c_S}$ 对应不同的时间位置。自回归反馈时，每步的输入表示聚合了先前生成的这些 token 的嵌入。生成结束后，得到的 $S \times T$ 码本矩阵（$T$ 为总声学帧数）经去交错（de-interleave）后送入声学解码器合成波形。

这种统一词表设计天然支持混合模态响应（如文本无缝过渡到音频）。

1.3 验证模型

模型 骨干 码本流数 编码器 场景
Bagpiper Qwen3-8B 8 X-Codec 开放式音频理解+生成，支持 CFG
OpusLM OLMo-2-7B 9 (1 SSL + 8 DAC) DAC ASR + TTS
OpusLM-Dialogue SmolLM2-1.7B 9 DAC 口语对话

2. 标准连续批处理引擎的局限（§2.2）

vLLM 等引擎通过迭代级调度和连续批处理最大化硬件利用：不等待整个 batch 完成，而是以单解码步为粒度动态注入新 prompt、退役已完成的请求。PagedAttention 将 KV 缓存分成固定大小的非连续块，按需分配 GPU 内存并消除碎片化。

核心约束：这些引擎将模型视为黑盒，对所有活跃请求执行统一的前向传播，整个基础设施深度耦合于”同构、单流文本生成”的假设。多 token 预测和 CFG 推理必须在此约束下工作。

3. 统一多 Token 预测服务管线（§2.3）

3.1 主-辅分解（Primary-Auxiliary Decomposition）

核心思想：不修改调度器和 PagedAttention，而是将一个码本流指定为”主流（Primary）”，由引擎标准管线全权管理。其余 $S-1$ 个”辅流（Auxiliary）”在模型的 logit 计算阶段内部采样并按请求缓冲。

从引擎的视角看，模型仍然是每步只发射一个 token 的标准文本 LM——但实际上透明地执行了多码本生成。

3.2 去交错与解码（De-interleave and Decode）

请求完成后，缓冲的码本矩阵经延迟去交错后传入同驻 GPU 的声学解码器，将波形合成直接融合进服务路径，消除了外部 vocoder 服务的需求。

3.3 混合模态阶段管理（Mixed-Modality Phase Management）

通过逐请求的阶段状态机配合动态词表掩码，系统在三个主要状态间转换：

  1. 文本阶段（Text Phase）：词表限制为文本 token
  2. 过渡阶段（Transition Phase）：注入确定性桥接 token 以条件化音频生成
  3. 音频阶段（Audio Phase）：激活所有 $S$ 个流

关键细节：

  • 排空子阶段（Drain Sub-phase）：音频阶段结束时发射 $S-1$ 个填充 token 以刷新延迟缓冲区，保证完整的 $S \times T$ 码本矩阵可供去交错。
  • 模态推断：由于连续批处理将多请求 token 交错为单一扁平序列，通过输入位置追踪模态不可靠。系统改为从模型未掩码的输出分布中动态推断活跃模态（即对不相交词表区域取 argmax），确保鲁棒且引擎无关的阶段管理。

4. 分类器无关引导的配对请求协同调度（§2.4）

CFG 对每个码本流 $i$ 独立应用：

朴素实现需要两个独立请求，引发严重的调度碎片化和跨请求同步开销，且由于需要逐步同步而不可行。

4.1 配对协同调度机制（Paired Request Co-Scheduling）

端到端流程（Figure 2 右侧）：

  1. 输入自动分配：当服务器收到 CFG scale $w > 1$ 的请求时，透明生成一个”伴侣请求（Companion）”（空 prompt）。引擎将此对视为原子调度单元，始终一起处理。
  2. 共享前向传播：二者被协同调度到同一连续 batch，共享单次 Transformer 前向传播。引擎严格按 50/50 平分逐步 token 预算。
  3. CFG 合并：前向传播后，两个上下文的原始 logits 按公式合并。合并仅在音频阶段执行，旁路模态切换 token 以防 CFG 破坏阶段状态机。辅流的投影一起批处理以避免冗余计算。
  4. 输出与同步：从合并分布 $\tilde{\ell}^{(i)}$ 中采样单一主 token，同步追加到伴侣请求（伴侣的外部输出对客户端隐藏），确保两个上下文在下一步保持完全相同的自回归历史。

5. 实验

5.1 实验设置

  • 硬件：单张 NVIDIA H100 80GB GPU，FlashAttention-3
  • 最大序列长度：16,384 tokens
  • 并发量：标准评估 512 请求，CFG 评估 256 请求（因内部伴侣请求等效工作负载相同）
  • 基线：原始 PyTorch 顺序推理管线（无连续批处理）

5.2 吞吐量

系统 Decode (tok/s) MFU (%)
Bagpiper (PyTorch) 52.7 0.096
Bagpiper (vLLM) 5694.5 9.95
OpusLM (PyTorch) 36.5 0.311
OpusLM (vLLM) 4582.9 9.89
OpusLM-Dial. (PyTorch) 53.9 0.290
OpusLM-Dial. (vLLM) 5870.5 3.28

关键发现：

  • 连续批处理管线实现了约两个数量级的加速（Bagpiper: 108×, OpusLM: 125×, OpusLM-Dialogue: 109×）。
  • MFU 从基线的不足 0.1% 提升至 Bagpiper 的 9.95% 和 OpusLM 的 9.89%。
  • OpusLM-Dialogue（1.7B 参数）虽然绝对吞吐最高（5870.5 tok/s），但 MFU 仅 3.28%。原因：如此紧凑的模型在 H100 上算术强度低，推理在完全饱和计算单元之前就撞到了内存带宽墙。

5.3 数值正确性与质量验证

使用 Bagpiper 在 MMAU-mini 数据集上验证 token 序列和 logit 分布的一致性：

5.4 CFG 开销分析

设置 Prefill (tok/s) Decode (tok/s) MFU (%)
w/o CFG 315.8 4952.0 8.0
w/ CFG 271.2 3960.7 12.8

CFG 保持了基线80% 的解码吞吐。效率来源于三个因素：

  1. 前缀缓存命中：伴侣请求严格复制主序列，实现近乎完美的前缀缓存命中，最小化 KV 缓存开销。
  2. 内存带宽受限的边际成本：自回归解码本质上是内存带宽受限的，处理伴侣请求仅相当于 batch size 的边际增加——饱和空闲计算以提升 MFU（从 8.0% 到 12.8%），延迟和同步惩罚可忽略。
  3. 阶段选择性激活：如 Bagpiper 等模型在输出简短音频前会生成大量文本推理。CFG 仅在短暂的音频阶段激活，有效地将双通道成本摊销到整个端到端序列上。

6. 结论与启示

本文的核心贡献在于证明了：在不重写推理引擎核心调度器的情况下，通过精心的架构设计（主辅分解 + 阶段状态机 + 配对协同调度），可以让专为文本设计的高吞吐引擎原生服务于多模态语音模型。修改仅局限于模型层和 logit 处理层，具有良好的可移植性。
