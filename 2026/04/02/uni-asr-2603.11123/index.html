Uni-ASR: Unified LLM-Based Architecture for Non-Streaming and Streaming Automatic Speech Recognition

本文最后更新于 2026年4月8日 下午

论文信息

  • 标题：Uni-ASR: Unified LLM-Based Architecture for Non-Streaming and Streaming Automatic Speech Recognition
  • 作者：Yinfeng Xia, Jian Tang, Junfeng Hou, Gaopeng Xu, Haitao Yao（阿里巴巴 Qwen 应用事业部 & 通义 AI 实验室）
  • arXiv：2603.11123

1. 背景与问题

1.1 LLM-based ASR 的崛起

近年来，语音识别（ASR）的技术路线正经历一场以大语言模型（LLM）为核心的范式转移。从 Whisper 以 1.5B 参数、68 万小时数据验证 Encoder-Decoder（AED）框架的规模化效果，到 Seed-ASR、FireRedASR、Fun-ASR、Qwen3-ASR、Index-ASR 等系统将 LLM 深度融合进识别解码链路，LLM-based ASR 已在语义消歧、上下文连贯性与转录流畅度等维度显著超越传统 AED。

然而，这类系统在低延迟流式场景（如实时字幕）中的部署依然是一个尚未完全解决的工程难题。

1.2 现有流式方案的两类范式及其局限

范式一：为非流式模型构造流式解码流水线

代表策略包括 hold-n、wait-k 和 local agreement。这些策略的核心思路是：不对模型架构或训练做任何修改，仅在推理阶段选择性地发出部分假设，从而抑制 chunk 边界处声学歧义导致的错误传播。

但这类方案存在两类内生缺陷：

  1. 计算冗余：每次增量推理都需要从头重新初始化解码过程，导致大量重复计算；
  2. 延迟不可预测：假设选择过程本身会引入不规则的延迟峰值。

范式二：原生流式 ASR 模型

代表性工作包括：

  • Transducer-Llama：将 LLM 集成进 Factorized Transducer 框架作为 non-blank 预测器，但将 LLM 仅用作辅助组件，语音-语言模态融合深度不足，制约了端到端协同优化；
  • SpeechLLM-XL / Speech ReaLLM：将语音-文本序列分段用于流式训练，但实验验证仅限于小型语言模型，可扩展性未经充分验证；
  • MoCha-ASR：采用单调 chunk-wise 注意力与 read-write 策略网络和 MinLT loss，端到端优化，但流式推理流水线复杂度显著提升。

核心矛盾：现有方案无法在一个统一架构中，同时保持非流式的高识别精度与流式场景的低延迟，且大多引入了架构修改或独立模型分支，增加了部署成本。

2. Uni-ASR 方法

Uni-ASR 的核心目标是：用单一模型、不改变架构，同时支持非流式与流式语音识别，并通过联合训练范式 + 上下文感知训练 + Fallback 解码策略，在不引入额外延迟的前提下提升流式识别精度。

2.1 模型架构

Uni-ASR 遵循主流 LLM-based ASR 的三组件架构范式（与 Seed-ASR、FireRedASR、Fun-ASR、Qwen3-ASR、Index-ASR 相同），由以下三部分构成：

  1. Audio Encoder：采用 Conformer 架构，从输入语音中提取高层语音表征。为保证流式模式下的严格因果性，Conformer block 中的标准深度可分离卷积被替换为因果卷积（causal convolution）。
  2. Audio Adapter：由两个线性层和中间 ReLU 激活构成，将语音表征映射到与 LLM 兼容的 embedding 空间。
  3. LLM Decoder：基于预训练的 Qwen3-1.7B 语言模型，以自回归方式生成转录文本，条件输入为编码器输出的语音表征以及用户提供的文本提示。

2.2 联合训练范式与专用解码策略

Uni-ASR 提出了一套集成训练-解码框架，核心是统一的联合训练范式配合专用解码策略，在单一端到端架构内无缝支持非流式和流式推理，无需维护独立的模型分支。

2.2.1 非流式范式（Non-Streaming Paradigm）

在非流式 ASR 中，模型一次性接收完整语音输入并生成转录。训练采用 teacher-forced 自回归框架：

  • 输入序列：将语音表征、起始标记 <sos> 和真实文本 token 按时间顺序拼接
  • 目标序列：将真实文本 token 前移一位，末尾追加结束标记 <eos>
  • 损失计算：交叉熵损失仅计算在目标文本 token 上，语音部分不参与损失

形式化表示（设语音表征序列为 $E_{1..n}$，文本 token 序列为 $y_{1..T}$）：

推理流程：在 prefill 阶段将完整语音表征一次性输入 LLM；在 decode 阶段逐 token 自回归生成，直到遇到 <eos> 停止。

2.2.2 标准流式范式（Standard Streaming Paradigm）

流式场景下，输入语音被切分为固定长度的 chunk。核心思路是将流式训练转化为多轮连续非流式训练实例：每个语音 chunk 被视为一个独立的识别任务，同时携带从先前片段传递来的上下文记忆。

具体操作步骤：

  1. 使用外部强制对齐工具（forced alignment）对 chunk 对应的转录文本进行对齐与分割；
  2. 按照预定义的 N:M 比例（实际配置为 2:1 的语音-文本 token 比例）将语音 token 与文本 token 交错排列；
  3. 每段内未占用的文本位置填充 <pad> token。

训练时构造交错语音-文本输入序列，与目标转录配对，实现端到端训练。

流式推理：语音输入以 chunk 为单位增量到达，prefill–decode 循环迭代执行直至完整语音收到。该流程被建模为一个多轮对话范式，在非流式推理框架内实现。关键机制是：

  • prefill 和 decode 阶段产生的 KV cache 跨 chunk 增量累积
  • 先前 chunk 的 cache 严格不可变，在后续处理中被高效复用

该机制在保证完整上下文连续性的同时，彻底消除了跨 chunk 的冗余计算。

2.3 上下文感知训练范式与 Latest-Token Fallback 解码策略

2.3.1 问题定位：训练-推理不一致性

在流式 ASR 中，识别输出在 chunk 边界处特别容易出现歧义，原因是上下文信息不足。现有方法如 Future-aware Transformer（FaT）和 Delayed Streams Modeling（DSM）通过 look-ahead 机制丰富上下文建模来缓解此问题，但这些方法会引入不可忽视的额外延迟。

Uni-ASR 的方案不引入额外延迟。具体地，基于 hold-n 策略，提出 Latest-Token Fallback 解码策略：

每个语音 chunk 的最后一个文本 token 暂时发出（以保证低延迟），并在处理下一个 chunk 时重新解码该 token。

这一策略产生了一个新的训练-推理不一致问题：后续 chunk 解码步骤的第一个文本 token 来自前一个 chunk，这在标准训练中完全没有被建模。

2.3.2 上下文感知流式训练范式（CS Training Paradigm）

为弥合上述 gap，引入上下文感知流式（Context-aware Streaming，CS）训练范式，通过对序列的两处针对性修改，使训练动态与推理行为对齐：

(i) 输入序列修改：将每个交错语音-文本段的最后一个文本 token 替换为 <pad>

(ii) 目标序列修改：从每个文本段中省略 <eos> 标记

这一设计有两重意图：

  1. 防止与 SS 训练范式混淆，保持训练信号的独立性；
  2. 通过在训练中刻意遮蔽最后一个文本 token，迫使模型学会识别跨 chunk 的上下文不连续性，并学会补全缺失的文本 token。

因此，在推理时，当增量解码遇到缺失的文本 token 时，模型会从指定上下文边界触发重解码（re-decoding）。

2.3.3 流式推理中的 Fallback 解码流程

在基于 Latest-Token Fallback 策略的流式推理中，当收到新的语音 chunk 时：

  1. LLM 丢弃前一解码轮次产生的 KV cache；
  2. 将输出序列中的最后一个文本 token 替换为 <pad>，重置输出序列；
  3. 将修订后的序列与当前语音表征拼接，作为 prefill 阶段的输入；
  4. 触发上下文感知的缺失 token 重生成。

整个操作严格在当前推理窗口内进行，计算开销可忽略不计，同时严格满足延迟约束。

3. 实验设置

3.1 数据处理

Uni-ASR 严格在中英文双语语料上训练（不包含其他语言）。训练数据来源包括：

  • 开源 ASR 数据集：AISHELL-1、AISHELL-2、WeNetSpeech、FLEURS、LibriSpeech、GigaSpeech
  • 内部标注语音数据

混合语料显著丰富了语内多样性（方言口音、说话风格、领域变化）和声学变异性，从而增强了模型在真实场景下的鲁棒性。

文本预处理：所有文本标签经过文本归一化（大小写标准化、去标点、数字转文字），以满足流式训练范式的约束。

字符对齐：通过 MMS FA（Meta 的多语言强制对齐工具）获得字符级对齐，聚合至 subword token 级别以支持 BPE 分词。对于中文文本，通过遮蔽多字符 BPE token 强制执行字符级切分，确保每个汉字在编码和对齐过程中被一致地视为独立语言单元。

3.2 Audio Encoder 的训练

以 FireRedASR-AED 的预训练权重初始化一个联合 CTC/AED ASR 模型，在 WeNet 框架内训练。

编码器在训练期间同时使用全注意力和动态 chunk 注意力，构建统一的非流式与流式语音处理框架。为保证流式模式下的严格因果性，Conformer block 中的深度可分离卷积被替换为因果卷积。

3.3 监督微调（SFT）

整个 SFT 阶段分为 5 个顺序阶段，按训练范式分为两大类：非流式 SFT（阶段 1-4） 和 联合 SFT（阶段 5）。

所有 SFT 阶段中，音频编码器始终同时使用全注意力和动态 chunk 注意力，保证整个训练过程中编码器对两种处理模式的兼容性。

SFT 阶段 Audio Encoder Adapter LLM 训练范式
1 🔒 冻结 ✏️ 训练 🔒 冻结 NS
2 ✏️ 训练 ✏️ 训练 🔒 冻结 NS
3 🔒 冻结 🔒 冻结 ✏️ 训练 NS
4 ✏️ 训练 ✏️ 训练 ✏️ 训练 NS
5 ✏️ 训练 ✏️ 训练 ✏️ 训练 NS / SS / CS

非流式 SFT（阶段 1-4）：每阶段的训练方法与主流 LLM-based ASR 框架的成熟实践保持一致（参见 Fun-ASR 技术报告），逐步解冻各模块以稳定训练。

联合 SFT（阶段 5）：在非流式 SFT 基础上，实现三种训练范式的统一联合训练：

  • NS（非流式）、SS（标准流式）、CS（上下文感知流式），以 1:1:1 的比例均匀采样。
  • 关键约束：SS 和 CS 范式仅在使用动态 chunk 注意力机制的训练步骤中激活，确保架构能力与训练动态的精确对齐。

5. 消融实验

5.1 Chunk 长度对流式性能的影响

流式识别存在一个基本的延迟-精度权衡：更短的 chunk 降低延迟，但因上下文不足导致更多边界切分误差，性能会显著下降。

量化分析——Chunk 长度影响（Beam Search 基准）：

  • 1000 ms → 640 ms：平均 WER 相对增加 +10.02%（3.39 → 3.73）
  • 1000 ms → 320 ms：平均 WER 相对增加 +32.15%（3.39 → 4.48）

较短 chunk 导致的显著性能退化，主要来源于数据碎片化伪影和边界转录错误。

5.2 Latest-Token Fallback 解码策略的效果

Fallback 策略在所有 chunk 长度下均带来一致性的性能增益，且chunk 越短，增益越显著：

  • 1000 ms：Greedy† vs Greedy，平均 WER 相对下降 11.43%（3.85 → 3.41）
  • 640 ms：Greedy† vs Greedy，平均 WER 相对下降 13.50%（4.22 → 3.65）
  • 320 ms：Greedy† vs Greedy，平均 WER 相对下降 19.88%（5.18 → 4.15）

值得注意的是，在相同 chunk 长度下，Greedy†（Greedy + Fallback）在性能上持平甚至超越标准 Beam Search（1000 ms：Greedy† Avg=3.41 vs Beam Avg=3.39），而 Greedy† 的计算成本远低于 Beam Search。这表明 Fallback 策略不仅提升了精度，还在推理效率上具有实际价值。

6. 结论

Uni-ASR 提出了一套统一的 LLM-based ASR 框架，核心贡献可归纳为三点：

  1. 联合训练范式（NS + SS + CS，1:1:1 均匀采样）：以单一模型同时支持非流式与流式推理，无需任何架构修改，非流式精度与 SOTA 方案竞争，流式性能显著超越同类原生流式框架；

  2. 上下文感知流式训练范式（CS）：通过对输入序列（遮蔽最后文本 token）和目标序列（省略 <eos>）的针对性修改，将 Fallback 解码行为直接内化到学习目标中，从根本上弥合训练-推理 gap；

  3. Latest-Token Fallback 解码策略：在不引入额外延迟的前提下，通过对上一 chunk 最后 token 的延迟纠错，实现跨 chunk 的上下文补全，在所有 chunk 长度下一致提升流式识别精度。

从工程实践角度，Uni-ASR 最大的价值在于单模型统一部署：同一套权重，通过不同的推理配置（全注意力 vs 动态 chunk 注意力，非流式解码 vs Fallback 流式解码），即可满足对精度要求高的离线场景和对延迟敏感的实时场景，显著降低了生产环境中的模型维护成本。
