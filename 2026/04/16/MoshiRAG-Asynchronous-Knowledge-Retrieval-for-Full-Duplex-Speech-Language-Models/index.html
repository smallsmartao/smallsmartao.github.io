MoshiRAG: Asynchronous Knowledge Retrieval for Full-Duplex Speech Language Models

本文最后更新于 2026年4月16日 上午

论文链接：arXiv 2604.12928
代码：GitHub - kyutai-labs/moshi-rag
Demo：moshi-rag.kyutai.org
作者：Chung-Ming Chien, Manu Orsini, Eugene Kharitonov, Neil Zeghidour, Karen Livescu, Alexandre Défossez
机构：Toyota Technological Institute at Chicago, Kyutai, Gradium

1. 引言

语音对话语言模型（Speech-to-Speech Language Models）正在成为提升对话式 AI 自然度的核心技术路径。其中，全双工模型（full-duplex models） 以其”边听边说”的能力区别于传统的基于轮次（turn-based）的方法——后者在处理完一整段语音（如一个句子）后才能在听和说之间切换（如图所示）。全双工模型能够同时接收语音输入并生成响应，从而更好地处理停顿、打断和反馈信号（backchannel），更贴近真实人类对话的复杂交互模式。

然而，全双工方法也带来了独特的挑战：实时语音处理和生成的需求。同时，近期研究表明，原生音频模型在需要事实性（factuality）的任务（如问答）上表现远逊于文本模型，部分原因是可用于训练的语音数据在词量上远少于文本数据。

为了在保持交互性的同时提升事实性，本文提出了 MoshiRAG——第一个具备检索增强生成（RAG）能力的全双工语音模型，构建于全双工语音 LM Moshi 之上。其核心洞察在于：利用口语响应开始到关键信息出现之间的自然时间间隙（keyword delay），在不中断对话流的情况下异步完成信息检索。

2. 相关工作

2.1 全双工语音模型

自 dGSLM 开创端到端多说话人对话建模以来，全双工模型已成为日益重要的研究方向。现有方法可分为两类：

  • 时分复用方法（Time-multiplexing）：如 OmniFlatten、MinMo，模型在固定时长的用户输入和等长的响应生成之间交替。
  • 双通道架构（Dual-channel）：如 Moshi、SALMONN-omni、FLM-Audio、PersonaPlex，以高帧率同时建模输入和输出语音流。

2.2 语音模型中的 RAG

为提升语音对话模型的事实性，近期工作如 WavRAG、VoxRAG 等已引入 RAG。与本文最相关的并行工作是 Stream RAG，它同样利用口语对话中的时间间隙来执行信息检索。但现有方法均针对非全双工场景设计，未能解决实时全双工对话中的严格时序约束。此外，现有方法通常从固定的预索引语料库中检索信息，而 MoshiRAG 将此范式扩展至开放域 QA，可直接从网络检索信息。

3. 系统设计

3.1 时序约束分析

本文首先定义了人机语音对话中与延迟相关的关键术语：

  • TTFAT（Time-to-First-Audio-Token）：用户发言结束到模型生成第一个音频 token 之间的延迟，即音频域的 TTFT。
  • Keyword Delay：模型口语响应开始到关键内容（直接回答用户查询的关键词）首次出现的时间间隔。
  • E2EKD（End-to-End Keyword Delay）：从用户查询结束到关键词在模型响应中被提及的总时间，即 TTFAT + Keyword Delay。
  • Retrieval Delay：从预测检索触发信号到检索过程完成的时间。

E2EKD 是一个关键的感知指标，决定了有意义的信息多快能传递给用户。对于检索增强系统，检索延迟必须短于 E2EKD，才能将检索信息及时整合到响应中。初步分析显示，现有语音 LM 的 E2EKD 通常超过 3 秒。据此，MoshiRAG 在数据构建和模型训练中将检索延迟目标设定为不超过 2 秒。

3.2 系统概览

本文将前端（front end） 定义为直接接收或生成音频以与用户实时通信的模块，后端（back end） 则不直接与用户交互。前端必须对用户输入提供即时反馈，后端则可优先保证事实性和推理质量。

MoshiRAG 以原始 Moshi 模型（略有修改）作为全双工前端，异步信息检索系统作为后端并行运行。此外，由于大多数信息检索系统基于文本，额外使用一个流式 ASR 模型将用户语音转录为文本用于检索。前端与后端之间缺乏同步，使系统能够“边听边说边思考”，类似于人类的认知能力。

在语音对话过程中，前端 Moshi 接收 Mimi codec 编码器编码的用户语音 token 作为输入，在独立通道中自回归地预测文本转录（带填充 token）和对应的语音 token。相对于原始 Moshi 的唯一修改是引入了：

  1. 特殊的检索触发 token ⟨ret⟩
  2. 参考文本编码器（reference text encoder）

当 ⟨ret⟩ 被预测时，系统从 ASR 和 Moshi 输出中收集用户与助手的文本转录，将聚合的对话上下文传递给检索后端。检索进行期间，前端 Moshi 继续全双工运行。

⟨ret⟩ 预测后、检索完成前生成的内容称为 pre-RAG content，通常包含对用户查询的粗略回答以及不需要领域知识的填充短语（如 “Let me check that for you…”）。检索完成后，检索到的文档经参考文本编码器编码后注入 Moshi，使模型能够基于外部知识生成更准确、详细的回答。

3.3.3 检索后端

⟨ret⟩ 被预测后，系统先等待 0.5 秒让 ASR 模型生成完整的用户发言转录，然后将对话转录发送至检索后端。本文考虑两种后端：

  • LLM-based 检索：提示 LLM 阅读对话上下文并生成简洁、事实性的参考文档。
  • Search-based 检索：使用 AI 优化搜索工具 Tavily 从网络获取实时信息并提取关键亮点。

4. 数据与训练

4.1 数据生成

MoshiRAG 的训练依赖合成数据，流程如下：

4.1.1 话题

从现有 QA 数据集中策划话题：

  • Natural Questions：约 307k 话题
  • HotpotQA：约 90k 话题
  • TriviaQA：约 76k 话题
  • 总计 474k QA 衍生话题

此外，使用 LLM 在特定专家领域生成对话话题，通过与 LLM 的迭代讨论，确定了 16 大类中的 111 个专家领域，使用 Gemma 3 27B 为每个领域生成 50 个对话话题，额外产生 5.5k LLM 生成的专家领域话题。

4.1.2 带参考文档的对话脚本

对每个话题，使用 LLM 生成模拟自然人机交互的多轮对话脚本，每个脚本附带支持知识密集型回复的参考文档。RAG 启用的回复由三段组成：

  • Lead portion：不依赖外部知识
  • Body portion：包含基于参考的内容
  • Tail portion（可选）：总结性收尾

生成使用三个 Gemma 3 27B LLM，各担不同角色：

  • User LLM：可访问话题和之前的对话上下文，但不能看参考文档
  • Moshi LLM：不直接观察话题，但可完全访问对话上下文和参考信息
  • Reference LLM：提供参考文档

为增加多样性和鲁棒性，设计了三种提示变体：

  • v1：围绕选定话题的基本对话
  • v2：用户更频繁地质疑 Moshi，包含更多来回交锋和论辩
  • v3：用户偶尔引入无关话题或闲聊

此外，为 QA 风格话题构建单轮子集。最终合计约 190 万 对话实例。

4.1.3 语音合成

使用多通道 TTS 模型将脚本转为音频。使用固定说话人作为 Moshi 的声音，从内部数据集随机采样另一说话人作为用户的声音。合成语音语料库的平均时长：多轮对话约 2 分钟，单轮子集约 15 秒。

5.2 延迟与计算消耗

与 vanilla Moshi 相比，MoshiRAG 的对话模板引入了约 1 秒的关键词延迟增加。但 MoshiRAG 的 E2EKD（3.1s）低于几乎所有竞争系统。计入检索开销后，计算成本仍与同规模模型相当（0.37 FLOPs/sec vs. Moshi 的 0.22）。

6. 消融实验与深入分析

6.1 信息注入策略

作者对比了两种信息注入方式：

  • 加法注入（Additive injection）：将参考嵌入加到 Moshi 输入嵌入上（如公式 2），输入序列长度不变。
  • 插入注入（Insertive injection）：将参考嵌入序列显式插入 Moshi 输入序列，增加序列总长度。

对两种参考编码器（T5 和 ARC-Encoder），插入注入一致优于加法注入，显示了信息整合效果与序列长度之间的明确权衡。T5 的性能差距更大，归因于其输出过长——加法注入下参考信息可能引入过晚。尽管插入注入效果更好，最终仍采用加法策略以限制序列长度，保持 Moshi 进行长对话的能力。

6.2 参考编码器选择

对比 T5 与两种 ARC-Encoder 变体（压缩比 4 和 8）：

6.3 ASR 和参考正确性的敏感度

MoshiRAG 对 ASR 错误高度敏感。使用 ground-truth 用户转录可将检索参考和最终响应的正确率提升高达 15%。提供 ground-truth 参考文档也能提升响应准确率，但 ref. 和 resp. 之间的差距也增大，反映知识整合过程中显著的信息损失。

6.4 多种检索后端

MoshiRAG 展示了出色的跨模型稳定性。当配对 GPT-4.1、Mistral Medium 3.1 或 Gemini 2.5 Flash 后端时，性能保持一致，表明 RAG 框架对底层检索器的语言特性基本无关。这意味着：

  • 高级模型（如 GPT-4.1）设定性能上界
  • 小型 LLM（如 Gemini Flash）以更低推理成本实现有竞争力的基准性能
  • 支持多后端实现冗余机制（如本地小 LLM 作为在线 API 的回退策略）

6.5 Full-Duplex-Bench v1.5

在处理重叠语音时，MoshiRAG 表现出更高的 Resume 倾向。关键的是，当用户真正打断时，MoshiRAG 响应用户输入的比例与 vanilla Moshi 相似，同时在 User Backchannel 和 Background Speech 场景中表现更好。

7. 结论

MoshiRAG 是首次将 RAG 整合到全双工语音语言模型的尝试。其核心贡献：

  1. 利用自然时间间隙：口语响应中查询结束到关键信息出现之间的时间窗口足以完成异步检索。
  2. 模块化、可插拔设计：检索后端可即插即用替换，无需重新训练。
  3. 事实性显著提升：超越大多数公开发布的 turn-based 语音 LM，同时保持全双工系统的高交互性。
  4. 工具使用泛化：在未明确训练的数学推理任务上展现强劲的分布外泛化能力。

未来方向包括：

  • 将检索触发与查询难度关联，或使用强化学习决定是否需要检索
  • 多样化检索工具集，使模型根据用户输入选择合适工具
  • 提升模型对检索过程中可能出现的错误的鲁棒性

MoshiRAG 展示了将实时交互语音界面与更强大的问题解决机制相结合的广阔前景，为构建更强大、可靠和用户友好的语音 AI 助手指明了方向。
