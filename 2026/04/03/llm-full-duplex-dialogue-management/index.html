LLM-Enhanced Dialogue Management for Full-Duplex Spoken Dialogue Systems

本文最后更新于 2026年4月8日 下午

论文信息

  • 标题：LLM-Enhanced Dialogue Management for Full-Duplex Spoken Dialogue Systems
  • arXiv：2502.14145
  • 作者：Hao Zhang, Weiwei Li, Rilin Chen, Vinay Kothapally, Meng Yu, Dong Yu（Tencent AI Lab）
  • 会议/时间：2025 年 2 月（arXiv v2）

1. 背景与动机

1.1 全双工为何困难？

人类对话天然是全双工（full-duplex）的：双方可以同时说话、随时打断、在停顿中填入”嗯””对”等回应，而不会打乱对话节奏。然而现有的语音对话系统（Spoken Dialogue System, SDS）大多仍工作在半双工（half-duplex）或”伪全双工”模式：系统必须等待用户说完，才能开始生成回复。这种设计导致交互延迟高、体验生硬，在用户有停顿或犹豫时尤为明显。

要实现真正的全双工通信，SDS 需要同时完成三件事：听（Listening）、说（Speaking）、思考（Thinking）。这三者的实时协调在工程和算法层面都面临严峻挑战：

  1. 干扰说话人（Interfering Speakers）：背景中其他人的语音可能触发 ASR 或对话管理错误，导致系统对不相关的语音作出响应。
  2. 用户停顿与犹豫（User Pauses & Hesitations）：用户在句中停顿不代表已说完，系统若仅依靠静音检测便会过早响应或延迟响应。
  3. 非故意打断（Unintentional Interruptions）：用户说”嗯””对””知道了”等回应词，或对他人说话，并不意味着要打断系统的应答。若系统将这类信号误判为真实打断，会无谓地中止自身输出。

1.2 现有系统的局限

近年来，全双工 SDS 的研究路线大致分为三类：

  • 独立神经网络模块：如 Shin et al.（2024）用语音事件检测实现实时查询更新，但对更广泛的交互场景处理能力有限；Lin et al.（DuplexConv, 2022）通过多模态模型检测用户状态，但语义理解仍较浅层。
  • 有限状态机结合 LLM：Wang et al.（NeuralFSM, 2024）将 LLM 与有限状态机结合，通过微调实现同步说话与倾听，但将对话管理嵌入大模型带来了较高的推理开销。
  • 端到端大模型：VITA（Fu et al., 2024）引入状态 token 和双工机制，Moshi（Défossez et al., 2024）集成基础 LLM 与小型 Transformer 进行实时流式预测。这类方法自动化程度高，但推理成本昂贵，且 DM（对话管理器）与 CDE（核心对话引擎）高度耦合，难以独立优化。

上述方法的共同问题是：缺乏语义层面的理解（依赖浅层声学或语言特征），或将高频对话管理决策与大模型推理绑定在一起，导致计算开销大、可扩展性差。

本文的核心思路是：设计一个轻量级语义 VAD作为专用对话管理器，将高频的实时决策从大模型中解耦出来，从而在交互质量和推理效率之间取得更好的平衡。

2. 系统总体架构

2.1 六大模块

论文提出的全双工 SDS 由六个模块串联组成（如论文 Figure 1(a) 所示）：

  1. AEC（Acoustic Echo Cancellation，声学回声消除）：去除系统自身扬声器输出对麦克风采集的干扰，这是全双工场景的前提条件。
  2. 声学 VAD（Acoustic VAD）：基于声学特征的说话人检测模块，设计上具有说话人感知和距离感知能力，利用距离信息与说话人嵌入区分目标说话人与背景声。
  3. ASR（Automatic Speech Recognition）：实时转录用户语音为文本 token 序列，作为后续语义理解的基础。
  4. 语义 VAD（Semantic VAD）：本文的核心贡献，基于 0.5B LLM 微调，在短时间间隔内持续推断下一步动作（详见第 3 节）。
  5. CDE（Core Dialogue Engine）：较大的 LLM，负责生成高质量回复。仅在语义 VAD 预测为 <|S-S|> 时被激活，从而避免在不必要时消耗资源。
  6. TTS（Text-to-Speech）：将 CDE 生成的文本合成为语音输出。

整个流程中，前四个模块以短时间间隔（short intervals）持续运行，保证实时响应能力；CDE 则按需激活，节省算力。

2.2 声学 VAD 与语义 VAD 的分工

模块 信息来源 主要能力 局限
声学 VAD 声学特征（能量、频谱等） 区分目标说话人与背景噪声/干扰 无法理解语义，对停顿/犹豫无能为力
语义 VAD ASR 文本 + 历史对话上下文 语义完整性判断、打断意图分析 依赖 ASR 质量，对纯声学干扰不敏感

两者互补：声学 VAD 先过滤掉非目标说话人的干扰，语义 VAD 再在文本层面做精细的意图与状态分析。

3. 语义 VAD 模块详解

3.1 四种控制 Token

语义 VAD 的输出是四个控制 token，每个 token 对应一种对话管理动作（论文 Figure 1(b)）：

Token 全名 含义 触发场景
`<\ C-L\ >` Continue-Listening 继续倾听 用户查询未完成（含停顿、犹豫）
`<\ S-S\ >` Start-Speaking 开始说话 用户查询已完成，激活 CDE 生成回复
`<\ S-L\ >` Start-Listening 开始倾听 真实打断（Real INT），系统停止说话
`<\ C-S\ >` Continue-Speaking 继续说话 非故意打断（Fake INT），系统继续输出

这四个 token 覆盖了全双工对话的两个核心任务：

任务一：用户状态检测（User State Detection）

  • 目标：判断用户是否说完。
  • 映射：<|C-L|>（未完成）→ <|S-S|>（已完成）。
  • 难点：语义完整性高度依赖说话风格和语言细节，存在天然歧义性（例如”今天天气……”后面接”怎么样”或”很好”是完全不同的意图）。

任务二：用户意图分析（User Intention Analysis）

  • 目标：在系统说话时用户开口，判断是否需要响应。
  • Real INT（真实打断）→ <|S-L|>：用户有意改变对话走向，如否定、追问、换话题。
  • Fake INT（虚假打断）→ <|C-S|>：用户只是回应词、对他人说话、无关评论，系统无需停止。

3.2 对话管理流程

语义 VAD 接收两类主要输入：

  1. 用户查询 token：由 ASR 模块实时产生的文本序列。
  2. 历史响应 token：CDE 已生成的回复文本（用于意图判断的上下文）。

工作流程如下（论文 Figure 1(c)）：

  • DM（即语义 VAD）在每个短时间间隔结束时预测下一个控制 token；
  • 若预测为 <|S-S|>，则将历史用户查询与系统响应传递给 CDE，触发回复生成；
  • CDE 生成完毕后，DM 自动切换为 <|S-L|> 等待新输入；
  • 系统说话期间，DM 持续监测用户是否发出打断信号。

这种设计使 DM 与 CDE 完全解耦：DM 不需要 CDE 的内部状态，两者可以独立优化和替换，具有良好的可扩展性。

3.3 为什么选用 0.5B LLM？

选择 0.5B 参数量的轻量级 LLM 作为 DM 有以下工程考量：

  • 实时性要求：DM 需要在毫秒级时间窗口内持续推理，大模型的推理延迟不可接受。
  • 任务复杂度：DM 的本质是分类与指令遵循，而非开放式生成。0.5B 规模的模型在经过针对性微调后，完全足以完成这类结构化决策任务。
  • 降低计算开销：高频运行的 DM 使用轻量模型，可将大量算力留给低频但高质量的 CDE 推理。
  • 独立可优化：轻量 DM 更新成本低，不影响 CDE 的训练与推理。

具体模型为 Hunyuan（孙et al., 2024）的 0.5B-dense-8k 版本，上下文窗口 8K，适合处理多轮对话历史。

4. 训练数据构建

由于目前不存在公开的全双工对话数据集（包含四种控制 token 标注），作者团队设计了一套完整的合成数据生成流程。

4.1 数据生成算法

生成流程（论文 Algorithm 1）如下：

  1. 随机选取话题与说话风格：话题池包含 200 个日常对话主题（天气、旅行、餐厅等），说话风格池包含 10 种用户 persona；
  2. 随机设定对话轮数：$n \sim \text{Uniform}(2, 12)$；
  3. 按概率分配交互类型：每轮以概率 $P_{\text{real}}$、$P_{\text{fake}}$、$P_{\text{incomplete}}$ 分别引入真实打断、虚假打断、不完整查询，否则为正常 QA；
  4. 生成 prompt：向 LLM API（腾讯元宝，Yuanbao）解释控制 token 的含义和使用规则，要求其生成带标注的全双工对话。

Prompt 包含以下要素：

  • 目标说明：生成允许用户打断助手的对话转录；
  • 助手行为规范：详细说明四个控制 token 的含义与对应动作；
  • 输出格式：{Round X (对话类型); User: <用户语句>; Sys: <带控制token的系统回复>}；
  • 自定义指令：指定轮数、话题和说话风格。

4.2 四阶段数据处理

生成的原始数据经过四个阶段处理：

阶段 内容 说明
数据生成 用 20,000 条 prompt 调用 Yuanbao API 直接生成全双工对话
数据清洗 过滤格式错误和控制 token 不正确的样本 保留率约 60%，对指令遵循能力有要求
后处理 对于 LLM 难以直接生成的场景，先生成普通 QA 再注入交互模式 补充清洗后样本不足的部分
数据增强 修改用户查询末尾标点以匹配 ASR 输出特征 提升实际应用中的鲁棒性

最终数据集包含 11,990 段对话，80,338 轮次，覆盖多种交互场景。各场景分布（论文 Figure 1(e)）：

场景类型 占比
Normal（正常 QA） 47%
Real INT（真实打断） 21%
Incomplete Q（不完整查询） 19%
Fake INT（虚假打断） 13%

值得注意的是，作者发现当某类极端场景（如真实打断或不完整查询）占比超过 50% 时，模型会产生过拟合，导致其他场景性能下降。这验证了均衡训练数据分布的必要性。此外，为防止微调降低基础模型的通用能力，训练集中同时混入了无打断的普通对话样本。

5.1 测试集构建

由于目前不存在公开的全双工 SDS benchmark，作者针对四种交互场景各生成 1,000 条测试样本（共 4,000 条），生成流程与训练数据相同但话题/风格池独立重建，确保测试集不与训练集重叠。

6. 设计选择的深层原因分析

6.1 为何将 DM 与 CDE 解耦？

全双工系统的核心矛盾是：对话管理决策需要高频实时执行，而高质量回复生成需要大模型。将两者绑定（如 NeuralFSM、VITA 的做法）意味着大模型需要每隔几十毫秒就推理一次，推理成本呈数量级增长。

本文的解耦设计本质上是一种任务感知的计算分配策略：将结构化、规则性强的决策任务（DM）交给轻量模型高频处理，将创造性、上下文复杂的生成任务（CDE）交给大模型按需处理。这与操作系统中”中断处理程序轻量、应用逻辑复杂”的设计哲学异曲同工。

6.2 为何用合成数据而非真实标注数据？

全双工对话数据需要细粒度的时序交叉标注（记录系统说话时用户何时插入、插入意图如何），这类数据在现实中极难收集和标注。合成数据的优势是：可按需控制场景分布（Real INT、Fake INT、Incomplete Q 的比例），并保证控制 token 的标注精确无歧义。代价是领域覆盖的多样性依赖话题池和 prompt 设计的质量。

6.3 为何采用 Instruction Tuning 而非端到端训练？

作者明确指出，目标不是让 DM 学会回答问题，而是让它”遵循结构化规则、在各种全双工场景中采取正确动作”。Instruction Tuning 范式正好契合这一目标：用少量高质量的指令数据微调，模型可以快速习得决策规则，同时保留基础语言理解能力。这也是为什么 60% 的数据保留率已足够——质量比数量更重要。

8. 结论与展望

本文提出了一种基于轻量级 LLM 的语义 VAD 对话管理器，通过预测四种控制 token（<|C-L|>、<|S-S|>、<|S-L|>、<|C-S|>）实现全双工语音对话系统的实时轮换管理。主要贡献包括：

  1. 设计了涵盖四种交互场景的控制 token 体系，将对话管理归结为结构化分类任务；
  2. 构建了 11,990 段合成全双工对话数据集，包含均衡分布的各类交互场景；
  3. 采用 0.5B LLM 作为 DM，在保持语义理解能力的同时大幅降低推理开销；
  4. 验证了语义 VAD 在真实录音测试中的有效性，总体准确率超过 93.5%。

局限与未来工作：

  • 目前仅在中文对话上验证，需要扩展至多语言；
  • 系统延迟（latency）尚未在论文中详细分析，是下一步重点；
  • 计划扩展以支持大型多模态模型；
  • 端到端语音输入（直接处理音频 token 而非依赖 ASR 文本）是长期目标。

全双工 SDS 的终极目标是复现人类对话的自然流动感——本文的语义 VAD 方案在计算效率与交互质量之间找到了一个务实的平衡点，为下一代语音助手的架构设计提供了有价值的参考。
