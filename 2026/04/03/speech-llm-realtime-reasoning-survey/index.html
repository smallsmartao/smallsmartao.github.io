Think While You Speak: A Survey of Real-Time Reasoning in Speech LLMs

本文最后更新于 2026年4月16日 下午

本文融合综述三篇 2025 年关于 Speech LLM 实时推理的代表性工作：Mind-Paced Speaking（arXiv:2510.09592）、Can Speech LLMs Think while Listening?（arXiv:2510.07497）、Mini-Omni-Reasoner（arXiv:2508.15827）。三篇论文从不同切面攻克同一核心难题：如何让语音大模型在保持实时响应的同时具备深度推理能力。

1. 背景与动机

1.1 为什么 Speech LLM 的实时推理如此困难？

语音大模型（Spoken Language Model，SLM）的目标是实现类人的自然对话：用户说话，模型听到后立即给出高质量的语音回复。这一目标在技术上面临三重根本矛盾。

矛盾一：延迟 vs. 推理深度。 Chain-of-Thought（CoT）推理是提升大模型准确率的关键技术——研究一致表明，让模型先”想清楚”再回答（Think-Before-Speaking，TBS）能够显著提升复杂任务的表现。然而在语音交互场景下，完整 CoT 生成往往需要数百甚至数千个 token，对应数秒的等待时间，严重破坏对话的自然性。

矛盾二：流式输出 vs. 自回归生成。 当前主流 SLM 均基于自回归（Autoregressive）Transformer，天然是串行生成的。语音输出需要实时流式合成，而推理 token 的生成必然占据本应用于语音合成的时间窗口。

矛盾三：语义连贯 vs. 交织生成。 一种直觉上的解决方案是将 think token 与 response token 交织（interleave）生成：生成若干推理 token，再生成若干回复 token，如此循环。然而，这种模式强制 LLM 在”思考模式”与”回复模式”之间频繁切换，破坏了推理链的语义连贯性，导致性能下降。

1.2 三篇论文的差异化切入点

本综述涵盖的三篇工作均在 2025 年提出，均聚焦于”如何让语音模型在实时输出的同时进行有效推理”，但各自从不同维度出发：

论文 核心范式 关键创新
Mind-Paced Speaking (MPS) Think-While-Speaking 双脑架构：Formulation Brain 生成推理，Articulation Brain 并行生成回复
Can Speech LLMs Think while Listening? Think-While-Listening 多流架构 + CoT 微调 + Question Completeness 指标引导提前推理
Mini-Omni-Reasoner Thinking-in-Speaking Token 级交错生成：2:8 的 response:reasoning token 比率

三者在时序上的共同逻辑是：不等推理完成就开始产生输出。但实现路径迥异，形成互补的研究图谱。

2. Mind-Paced Speaking（MPS）：双脑框架

2.1 问题定义：顺序生成的延迟瓶颈

这一范式的首 token 延迟（First-Token Latency）等于生成全部 $T_c$ 个 CoT token 所需时间。在 Spoken-MQA 基准上，作者测量到 TBS 方法（MPS-tbs）在生成第一个回复 token 之前平均需要额外生成 762 个 token，对实时对话而言代价极高。

2.2 架构设计：Thinking Brain vs. Speaking Brain

MPS 的核心洞察来自认知神经科学：人类大脑中，负责高级认知推理的前额叶-颞叶网络（prefrontal-temporal cortex）与负责语音运动控制的运动皮层-皮下通路（motor cortex and subcortical pathways）是两套高度专业化且并行协作的系统。语言产生并非严格的”先思后说”，而是思考的后半段与表达的前半段在时间上重叠的增量过程。

受此启发，MPS 将单个 LLM 拆分为两个独立但共享参数的 LLM：

  • Formulation Brain（构想脑）：专注于理解用户意图，执行逐步 CoT 推理，持续生成”think token”段。
  • Articulation Brain（表达脑）：接收 Formulation Brain 实时产出的 think 段，结合历史推理与回复内容，逐段生成”response token”并送入流式 TTS 合成语音。

关键区别在于：Articulation Brain 无需等待 Formulation Brain 完成全部推理。每当 Formulation Brain 产出一个 think 段 $S^{\text{cot}}_n$，Articulation Brain 即刻基于目前已有的推理内容生成对应的回复段 $S^{\text{res}}_n$。

2.3 核心机制

将 CoT tokens $Y^{\text{cot}}$ 切分为 $N$ 段 $[S^{\text{cot}}_1, S^{\text{cot}}_2, \ldots, S^{\text{cot}}_N]$，Articulation Brain 的分段生成过程可写作：

每个 $S^{\text{res}}_n$ 的生成以 $\langle \texttt{}\, S^{\text{cot}}_{1:n}\, \texttt{} \rangle$ 为前缀，确保回复段与当前已知推理内容保持语义对齐。

MPS 的两种时序变体：

  • MPS-thkfirst（Think-First）：Formulation Brain 先生成 $T_c$ 个 think token，Articulation Brain 随即生成 $T_r$ 个 response token 并合成语音。首 token 延迟 = $T_c$ 个 token 的时间 + 流式 TTS 缓冲，通常约 80 个 token。
  • MPS-spkfirst（Speak-First）：Articulation Brain 先生成第一段回复，同时 Formulation Brain 同步开始生成第一段 think。延迟 ≈ 0（仅 TTS 缓冲）。

Think-incomplete SFT（不完整推理监督微调）：为使 Articulation Brain 能够基于部分推理内容产出合理回复，论文设计了专用训练数据构造策略：随机保留多步骤 CoT 的前 $L$ 步，删去后续内容，以 <think>...(不完整 CoT)...</think> 加上完整 response 作为训练样本。这一设计使 Articulation Brain 学会”以不完整思路给出回答”，从而在推理链逐步到来时保持回复质量。

推理阶段，$T_c = 80$，$T_r = 100$（其中 100 个 response token 对应 20 个文本 token + 80 个语音 token，即 ta4 格式）。

3. Can Speech LLMs Think While Listening？：CoT 与多流架构

3.1 问题：监听时如何同步推理

上述 MPS 及类似工作解决的是”说话时如何思考（Think-While-Speaking）”——即输出 response 与 CoT 并发。然而，仍存在另一个更早阶段的延迟：用户说完问题之后、模型开始生成 CoT 之前。

Meta 的工作《Can Speech LLMs Think while Listening?》提出了互补的视角：边听边想（Think-While-Listening）。其核心观察来自神经科学：人类在倾听时并非被动接受，而是实时预测和推理。当问题的主要信息量已经传达（即使用户尚未说完），人类便开始在心中构思答案。能否让语音模型复现这一认知模式？

3.3 CoT Fine-tuning 策略

为何用文本 CoT 而非语音 CoT？ 论文通过 GSM8K 消融实验证明，文本 CoT 与语音 CoT 在准确率上持平（17.5% vs. 17.2%），但文本 CoT 的序列长度仅为语音 CoT 的 1/3（119.0 ± 54.4 vs. 368.8 ± 190.3 个 token）。这从信息密度的角度解释了选择：文本每 token 携带更多语义信息，因此相同推理内容用文本表达更高效。

CoT 在 text monologue 流中的嵌入方式： 使用 <start_cot> 和 <end_cot> 特殊 token 在 system text 流中划定推理区域；同时引入流式 ASR（Streaming ASR） 将用户语音转录文本插入 text monologue 流（右移 $k=6$ 个 token，约 480ms 的前瞻延迟），帮助模型建立用户问题文本与 CoT 之间的语义关联。

4. Mini-Omni-Reasoner：Token 级别的 Thinking-in-Speaking

4.1 Thinking-before-Speaking 的局限

Mini-Omni-Reasoner（来自南洋理工大学、腾讯等机构）指出了”思考前说话”范式的两条失败路径：

  1. 全量语音化（Full Verbalization）：将推理过程和回复都转换为语音输出。结果是用户需要耐心听完整个推理链才能获得答案，认知负担极重（Qwen2.5-Omni 在 Spoken-MQA 多步推理上平均输出 116.1 个词，对话时长过长）。

  2. 静默推理（Silent Reasoning）：推理 token 不合成为语音，只有回复 token 合成。代价是等待推理完成的首 token 延迟——对于需要长链推理的复杂问题，该延迟可长达数十秒。

两种路径均无法同时满足正确率高、延迟低、输出简洁三个目标。

4.2 Token 级交错生成机制

核心创新： Mini-Omni-Reasoner 利用了一个硬件层面的不对称性——现代 GPU 上大型语言模型的 token 生成速率（>100 tokens/s）远超音频播放速率（~12.5 tokens/s，对应 Mimi 编解码的帧率；或约 20 tokens/s 用于流畅语音合成）。

基于此，模型以固定比率 $p:q = 2:8$ 交错生成 response token 和 reasoning token：

reasoning token $t^{\text{reason}}$ 保持静默，仅作为后续 response token 生成的上下文。

比率设计的三重理由：

  1. 可控性：短回复块（2 个 token）避免过多语音输出先于充分推理。
  2. 推理容量：4 倍于回复的推理 token 保证足够的内部推演深度。
  3. 实时兼容性：3B 模型以 100 tokens/s 生成，每秒约输出 20 个 response token（约 5 个词），满足流畅语音合成需求。

控制 token 设计： 论文比较了三种策略——无显式标记、有显式标记（含损失加权）、masked 标记（插入切换 token 但从 loss 计算中屏蔽）。实验证明 masked 策略最有效：避免过拟合到 split token，同时在推理时通过手动插入 marker 引导生成模式。每个推理块后额外附加 8 个 padding token，以稳定下游 Talker 的对齐。

4.3 训练方法与数据

SPOKEN-MATH-PROBLEMS-3M 数据集： 针对语音数学推理，从公开文本数学数据集（GSM8K、MetaMath、Orca-Math、SingleOp 等）重采样 300 万样本，经四阶段流水线构建：

  1. 数据收集：聚合多样化数学题文本语料（~3.2M 题）。
  2. 口语化改写：每道题生成两种风格（保留原句式 / 转为对话口吻），答案分为符号化推理轨迹 + 简洁口语回复两路。
  3. TTS 合成：用 CosyVoice2-0.5B 将问题合成音频；按 2:8 比率将 reasoning + response 文本 token 化并交错。
  4. GPT 验证（Anticipation Drift 检测）：反交错还原后，由 GPT 检查是否存在”超前说话”（verbal token 先于对应推理出现）；未通过者丢弃。

关键挑战——Anticipation Drift（超前漂移）： 交错生成时，若 response 流推进过快，verbal content 可能先于其逻辑依据出现，导致模型产生幻觉或错误答案。解决方案：（1）要求 reasoning 序列从第一 token 起即进入实质推理，不允许冗余前缀；（2）要求 response 序列以轻量上下文化（如”Okay, let me try…”）开头，推迟实质内容，为推理建立时间缓冲。

五阶段渐进训练策略：

阶段 任务 冻结模块 可训练模块
1. Alignment 音频适配 音频编码器 适配器、嵌入层
2. Mixed Math Pretraining 文本/语音 TBS 数学 音频编码器 全部 Thinker
3. Textual TiS 文本输入，交错生成 音频编码器、适配器 LLM（Thinker）
4. Acoustic TiS 语音输入，交错生成 全部 Thinker（LLM） 音频编码器
5. Talker Training 语音合成 全部 Thinker Talker

这一渐进策略将”推理能力迁移到语音”与”语音生成对齐”解耦，避免了多目标同时优化带来的不稳定性。

训练配置：32 块 NVIDIA H100 GPU，3M 样本，6 个 epoch，batch size 64，cosine decay，最大学习率 2e-4。

5.2 各自的适用场景与局限

Mind-Paced Speaking：

适用场景： 对话质量要求极高、具备双 GPU 部署能力的生产级语音助手（如客服机器人、智能硬件）。双脑设计在 URO-Bench 的复杂对话任务中表现尤为突出，MPS-thkfirst 在中文/英文全部主要任务上超越 GPT-4o Audio 和 Step-Audio 2。

局限： (1) 需要两路 LLM 并发推理，计算资源消耗约为单模型两倍；(2) think 段与 response 段之间的段大小（$T_c = 80$，$T_r = 100$）为超参数，不同任务需要调整；(3) 当前实验仅在 Step-Audio 2 骨干上验证，通用性有待扩展。

Can Speech LLMs Think While Listening?：

适用场景： 问题语义在说完前已大部分确定的场景（如多选题、常识问答）；对延迟极度敏感且可接受少量精度损失的实时语音交互系统。QC 指标提供了细粒度的准确率-延迟调节旋钮（通过调整 $\theta$）。

局限： (1) 当模型过早触发 CoT 而后续信息至关重要时（如 Example 3 中”get a job”这一关键词在 CoT 启动后才出现），模型可能推理错误，Correct-DPO 虽有改善但未完全解决；(2) Moshi 基础模型在 GSM8K 仅达到 16.1%，与 text LLM 仍有较大差距，说明音频-推理的模态对齐仍是瓶颈；(3) 流式 ASR 引入 480ms 固定延迟，对超低延迟场景仍有约束。

Mini-Omni-Reasoner：

适用场景： 边缘部署或计算资源受限的场景（3B 参数），需要输出简洁且无额外延迟的数学/逻辑推理任务。

局限： (1) 2:8 的固定交错比率是针对当前硬件吞吐和 Mimi 帧率的经验值，在不同部署平台上可能需要重新校准；(2) 训练数据高度集中于数学题（SPOKEN-MATH-PROBLEMS-3M），迁移到开放域对话时泛化能力有待验证；(3) Anticipation Drift 问题在 GPT 验证筛选后虽已减轻，但在高度不确定性的开放域推理中仍可能出现。

6. 展望

6.1 当前主要未解决问题

问题一：推理长度自适应控制。 三篇论文的推理 token 数量均为固定设置（MPS 固定 $T_c = 80$，Mini-Omni-Reasoner 固定 2:8 比率）。对于简单问题，过多推理 token 是浪费；对于复杂问题，固定 token 数可能不够。如何让模型动态感知推理深度需求、自适应分配 CoT 资源，是尚未充分解决的问题。文本 LLM 领域已有 ThinkLess、ConciseRL 等尝试，但迁移至语音模态面临额外挑战。

问题二：全双工推理交互。 当前研究均假设用户单轮发问模型回复，而在真实对话中，用户可能在模型推理或回复过程中插话、打断或追问。如何在流式推理-说话框架中处理用户插话（TurnTaking），维护推理状态的连贯性，是全双工系统的核心未解难题。

问题三：多模态推理的一致性。 语音模态承载的信息（语调、情感、停顿）与文本推理链之间的对齐至今缺乏显式建模。例如，当用户语气表明困惑时，模型的 CoT 是否应调整推理策略？这一”副语言感知推理”尚未被任何现有系统系统性解决。

问题四：推理的可解释性与可控性。 三篇论文中的 CoT 均为内部状态（silent reasoning），缺乏对推理过程的可解释性保障。如何在保持低延迟的前提下，让推理链对用户透明（如可选的”思考摘要”），是面向实际应用的重要研究方向。

6.2 未来方向

方向一：强化学习优化推理策略。 DeepSeek-R1、GRPO 等在文本 LLM 上验证了 RL 对推理能力的显著增益。将 GRPO 等方法迁移至语音模态，以 Spoken-MQA 等基准的准确率为奖励信号，是可预期的下一步。初步探索（如 SARI 等工作）已显示潜力。

方向二：统一的推理-延迟帕累托建模。 当前各论文独立优化自己的延迟-准确率权衡，缺乏跨方法的统一理论框架。建立以”有效推理 token 利用率”为核心指标的分析框架，将有助于系统性比较和改进不同范式。

方向三：轻量化与端侧部署。 Mini-Omni-Reasoner 已将模型压缩至 3B，但端侧（手机、耳机、智能眼镜）部署还需要进一步的量化、剪枝与知识蒸馏。如何在 <1B 参数规模下维持有效推理，是面向消费级硬件的核心挑战。

方向四：多轮对话中的推理状态维护。 当前工作均聚焦于单轮推理场景。多轮对话中，跨轮次的推理上下文如何高效保存和检索（类似 KV-cache 的语音推理缓存），是实现真正”持续思考”对话系统的关键技术问题。

方向五：评测基准的完善。 Spoken-MQA 和 SRQA 目前主要覆盖数学与常识推理，缺乏对情感推理、创意思维、专业知识（医疗、法律）等场景的覆盖。构建更全面的语音推理基准，是推动领域进步的基础工作。
