再谈BPE分词

本文最后更新于 2026年4月3日 下午

三年前我写过一篇 BPE 分词算法，当时是在做 ASR 实验时好奇建模单元的划分原理，记录了一些基础概念。那篇文章只讲了 BPE 的基本流程，时间过去三年，大模型时代对 BPE 的理解需要深很多。

这篇文章在原有基础上补全那些当时没讲到的部分：词表该多大、中英文为何效率差这么多、tiktoken 和 SentencePiece 怎么选、以及生产环境里那些让人头疼的分词坑。

1. BPE 基础回顾

1.1 算法流程

旧文里描述的 BPE 流程是面向 ASR 建模单元的版本。LLM 时代的 BPE 在细节上有一些演变，这里重新梳理一遍。

BPE（Byte Pair Encoding）最早是 1994 年 Philip Gage 提出的数据压缩算法，2016 年 Sennrich 等人将其引入 NLP，现在 GPT、Llama、Claude 等主流模型全部采用。

核心思路只有一句话：找到语料里出现频率最高的相邻 token 对，合并成一个新 token，不断重复。

具体流程：

Step 1：初始化词表。 以 Byte-level BPE 为例（GPT-2 起采用），基础词表是 256 个字节值。任何文字——中文、emoji、特殊符号——都能用字节表示，彻底消除 OOV（未登录词）问题。旧版本的词符级 BPE 则是从字符集出发，旧文里描述的是这个版本。

Step 2：统计频率。 遍历语料，统计所有相邻 token 对的出现次数。

Step 3：合并。 选出最高频的 token 对，合并为新 token 加入词表，语料中所有对应位置替换。

Step 4：重复。 重新统计，继续合并，直到词表达到预设大小。

推理时的切分： 不再看频率，而是按训练时学到的合并规则，按优先级顺序依次执行。给定新文本，先拆成字节，再按规则逐步合并，输出最终 token 序列。

一个例子：BPE 训练时从未见过 “lowest” 这个词，但学到了 “low” 和 “est”。推理时 “lowest” 被切为 ["low", "est"]，模型依然能理解词根与后缀的关系。

1.2 与旧文的区别

旧文里描述的是词符级 BPE（word-level pre-tokenization 后在字符上做 BPE），每个单词开头加 _ 标记，合并不跨越词边界。这是 Sennrich 2016 年论文的经典实现，也是早期 ASR 系统常用的方式。

现代 LLM 普遍采用 Byte-level BPE，从字节出发，256 个字节作为基础词表，没有 OOV，覆盖所有 Unicode 字符。

2. 词表该多大

2.1 词表大小与模型规模的幂律关系

词表越大并非越好。NeurIPS 2024 论文 Scaling Laws with Vocabulary（Sea AI Lab & HKU）专门研究了这一问题，核心结论是：词表大小和模型参数量之间存在幂律关系，大多数 LLM 的词表都太小了。

以 Llama 2-70B 为例，最优词表应在 216K 以上，而实际只有 32K，差了 7 倍。

词表大小影响三件事：

压缩效率（token 数量）。 词表越大，同一段文本切出的 token 数越少。Llama 2（32K 词表）编码同一段文本比 Llama 3（128K 词表）多 30–40% 的 token。token 少意味着序列短，推理更快，上下文能容纳的信息更多。

Embedding 层参数量。 词表扩大，Embedding 矩阵随之膨胀：$\text{vocab_size} \times \text{hidden_dim}$。Llama 3-8B 的 $128{,}000 \times 4{,}096 = 5.24$ 亿参数，仅 Embedding 就占总参数的 6.5%。对小模型来说这个比例很高，数据不够或模型规模不足时，词表反而要保持小一些。

多语言支持。 Llama 3 扩词表的主要动机之一是改善非英语语言的编码效率。32K 词表里中文 token 太少，很多汉字被拆成 2–3 个字节级 token；128K 词表能给中文、日文、韩文分配更多专属 token。

2.2 各规模模型的经验参考

模型规模 推荐词表大小 代表模型
< 1B 32K Phi 系列
1B – 13B 32K – 64K Mistral 7B（32K）
13B – 70B 64K – 128K Llama 3（128K）
> 70B 128K – 256K Gemini（256K）

实验数据：同样的计算预算（$2.3 \times 10^{21}$ FLOPs），词表从 32K 扩到 43K，ARC-Challenge 准确率从 29.1% 提升到 32.0%，差了近 3 个百分点。

2.3 词表太大的边际递减

超过 100K 之后边际收益递减明显。从 8K 到 32K，困惑度（perplexity）下降显著；从 100K 到 200K，改善已经很小，但 Embedding 层参数和内存占用在线性增长。

2.4 SuperBPE：更高效的合并策略

SuperBPE（COLM 2025，华盛顿大学 + NVIDIA + AI2）提出两阶段 BPE：先学子词内部的合并，再学跨词边界的”超级词”（如 “by accident”、”of course” 这类固定搭配）。

结果：同样 200K 词表，SuperBPE 比标准 BPE 减少 33% 的 token，在 30 个 benchmark 上平均提升 4.0%，MMLU 提升 8.2%。Moondream AI 已在产品中采用，序列长度平均缩短 21%。

3. 为什么中文调 GPT-4 API 比英文贵

3.1 分词器的语言偏见

一个中文字在 GPT-4 里占几个 token？答案是 1–3 个，常见汉字通常是 1–2 个，但远比英文单词效率低。

根本原因：BPE 的合并规则从训练语料里学来，GPT-4 的训练数据以英文为主，英文字母组合频率高，学到大量高效合并规则（”tion”、”ing”、”the” 都是单个 token）。中文在训练数据中占比低，汉字组合频率不够高，能合并成完整 token 的词非常有限。

3.2 具体数据对比

文本 GPT-4 token 数 Qwen token 数 Claude token 数
“machine learning” 2 3 2
“机器学习” 4 2 3
1000 字英文 ~1,300 ~1,400 ~1,300
1000 字中文 ~1,800 ~900 ~1,500

同样 1000 字的内容，中文在 GPT-4 上比英文多约 40% 的 token，API 费用差 30–50%。

3.3 跨语言不公平问题

这不是某个模型的问题，而是英文主导的 BPE 分词器的通病。2023 年的研究（arxiv 2305.15425）发现，同一段文本翻译成不同语言后，token 数量最多能差 15 倍。低资源语言（泰语、阿拉伯语等）被严重碎片化，序列变长，不仅推理慢、API 贵，还因为上下文窗口被浪费而影响模型表现。

3.4 隐蔽的语义切割问题

MIT Press 2025 年的研究发现，GPT-4、GPT-4o 和 Llama 3 在处理中文时会被 token 边界误导——两个毫不相关的汉字，如果碰巧被切成了相同的开头 token，模型会错误认为它们语义相似。Llama 系列还会错误合并不存在的词（把”的事”当成一个词而非”事物”的一部分）。这类问题在日常对话里不明显，但在情感分析、法律文本等需要精确语义理解的场景里影响很大。

3.5 省钱的工程策略

  • 中文业务优先选中文优化模型。 Qwen 和 DeepSeek 的分词器针对中文专门优化，词表中包含大量中文高频字词，比 GPT-4 少 40–50% 的 token。
  • 混合语言策略。 系统 prompt 用英文写（消耗更少 token），用户输入保持原语言。
  • 推理语言切换。 DeepSeek R1 和 Qwen 3 用非英语语言推理，token 消耗比英文少 20–40%。Qwen 3 用韩语推理甚至可省 73% 的 token。

4. tiktoken 与 SentencePiece 怎么选

4.1 核心区别

两者都实现了 BPE，但处理顺序不同：

tiktoken 的流程： 文本 → 正则预分词（按空格、标点切开）→ UTF-8 编码成字节 → 在字节上做 BPE 合并。合并不能跨越预分词产生的块边界。

SentencePiece 的流程： 文本 → 直接在 Unicode 码点上做 BPE 合并，不需要预分词。空格用 ▁ 表示，和其他字符一视同仁参与合并。

4.2 实际影响

维度 tiktoken SentencePiece
多语言处理 正则规则面向英文，中日韩等无空格语言效果较差 无预分词依赖，多语言友好
速度 Rust 实现，比 SentencePiece 快 3–6 倍 Python/C++ 实现，速度较慢
训练支持 不支持训练，仅推理 支持训练 + 推理
合并结果 预分词限制合并边界，某些情况导致次优合并 无边界限制

tiktoken 的关键限制：只能推理，不能训练分词器。要训练自己的分词器，必须用 SentencePiece 或 HuggingFace Tokenizers 库。

4.3 各模型的选择

分词器 使用模型
tiktoken GPT-3.5/4/4o、Llama 3
SentencePiece Llama 2、T5、Qwen、多数多语言模型
Mistral Tekken Mistral Nemo（基于 tiktoken，131K 词表）
HuggingFace Tokenizers 自训练分词器首选

Llama 3 从 SentencePiece 切换到 tiktoken 是个标志性事件，同时词表从 32K 扩到 128K，编码效率和推理速度均有提升。

4.4 训练自己的分词器

几百万 token 的数据就够，分词器只需学 token 频率，不需要理解语义。关键配置：

  • 用 SentencePiece 时必须设 byte_fallback=True，否则遇到罕见字符会报 unknown token
  • 词表大小参考 §2.2 的经验法则
  • 训练数据分布要和模型训练数据一致，否则容易产生 Glitch Token（见下节）

5. 生产环境的三个坑

5.1 Glitch Token

2023 年有人发现，让 ChatGPT 复述 “SolidGoldMagikarp” 这个词，它回复的却是 “distribute”。这不是幻觉，而是 Glitch Token。

原因：SolidGoldMagikarp 是一个 Reddit 用户名，在分词器的训练语料（网页文本）里频率够高，被合并成了独立 token。但在模型的训练数据里，这个 token 几乎没出现过，对应的 Embedding 向量基本是随机值，模型遇到它就”懵”了。

典型症状（来源：ACM 2024 论文）：

  • 幻觉：让模型复述一个词，输出完全不同的词
  • 拼写突变：Llama 2 复述 “wurden” 输出 “werden”
  • 随机字符：Mistral 7B 复述 “}}\^” 输出 “^^^^”
  • 拒绝回复或反复重复问题

检测与防御：

  • GlitchHunter（ACM 2024）：基于 embedding 空间聚类检测异常 token，在 7 个主流 LLM 上测试了 182,517 个 token
  • GlitchMiner：基于梯度的检测方法，用熵损失函数量化预测不确定性，precision 高于 GlitchHunter
  • LiteToken（arxiv 2602.04706，2026 年）：发现约 10% 的词表 token 是 BPE 合并的中间残留——训练时频繁出现，但最终几乎不被使用。删掉这些 token 能减少碎片化，提升对噪声输入的鲁棒性，无需重新训练，已在 Qwen3-8B、Llama-3.1-8B 上验证通过

5.2 数字切分导致算术错误

让 GPT-4 计算 $1234 + 5678$，有时会算错。问题不全在 Transformer 的计算能力，分词也是原因之一。

“480” 可能是一个 token，”481” 却被切成 “4” + “81”。数字的 token 切分是不规则的，模型无法稳定地对齐数位。

Llama 系列的做法是逐位切分——“1234” 切成 "1" "2" "3" "4"，只需 0–9 十个 token。这让模型的算术能力明显提升，代价是数字序列变长。DeepSeek V2 也采用了同样的策略。

工程建议：

  • 算术精度要求高的场景，用 Code Interpreter 而非让模型直接计算
  • 格式化数字输入，避免千分位分隔符干扰（”1,234” 和 “1234” 的 token 切分完全不同）
  • 了解所用模型的数字分词策略：Llama 系列逐位切分，GPT 系列混合切分

5.3 Token Healing：Prompt 边界偏差

这是最隐蔽的一个坑。假设 prompt 以 http: 结尾，期望模型补全 //www.example.com。但实际输出可能是带奇怪空格的 URL。

原因：训练时 :// 是一个完整 token（GPT-2 里是 token 1358）。prompt 在 : 处截断，模型看到的是单独的 : token（token 27），与训练时的分布不一致，生成偏离预期。

约 70% 的常见 token 都存在这个问题——它们是更长 token 的前缀，当 prompt 恰好在这里截断时就产生 token 边界偏差。

解决方案：Token Healing，由微软 Guidance 库（20K+ GitHub Stars）提出。核心思路：生成时回退一个 token，把 prompt 的最后一个 token 作为前缀约束，让生成的第一个 token 自然接上。

Token Healing 目前主要在本地推理时有效。调 API 时的规避方式：prompt 尾部不要截断在单词或符号的中间，保持完整的 token 边界。

6. 总结

主题 核心结论
BPE 基础 字节级 BPE 消除 OOV，推理按固定合并规则执行
词表大小 与模型规模幂律相关，Llama 2-70B 最优词表约 216K
中英文差异 GPT-4 中”机器学习”占 4 token，Qwen 只占 2 个；中文 API 成本高 30–50%
tiktoken vs SentencePiece tiktoken 快 3–6 倍但不能训练；多语言和自训练用 SentencePiece
Glitch Token 约 10% 词表是残留 token，可用 LiteToken 无损清理
数字切分 逐位切分提升算术能力，混合切分存在不规则性
Token Healing 70% 常见 token 存在边界偏差风险，Guidance 库可修复

分词器是大模型最被低估的组件。从 SuperBPE 到 LiteToken，学术界一直在这个方向挖潜——同样的模型参数，换个更好的分词器就能在 benchmark 上提升 4–8%。做应用的人往往只把 token 当计费单位，但它实际上是模型理解世界的最小粒度，值得认真对待。
